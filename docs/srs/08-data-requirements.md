## 3.6.1 Ownership

Each service owns one PostgreSQL database and its Prisma schema (`services/<name>/prisma/schema/*.prisma`, one file per module). No service reads another's tables. Data another service needs travels in events or through the internal calls in [3.4.4](06-external-interfaces.md#344-software-interfaces-internal-synchronous-calls). The entity-relationship diagrams are in [docs/architecture/diagrams.md](../architecture/diagrams.md#11-data-owned-by-each-service).

| Service | Tables (Prisma models) | Personal data |
|---|---|---|
| identity | `User`, `RefreshToken`, `UserToken` (verify/reset), `Store`, `Membership`, `Invitation`, `AuditEvent`, `OutboxEvent` | seller and member name, email, phone |
| orders | `Order`, `OrderItem`, `CallAttempt`, `ConfirmationSettings`, `CallScript`, `BlacklistEntry`, `ConfirmationLink`, `AuditEvent`, `OutboxEvent`, `ProcessedEvent` | **customer name, phones, address** (the only full copy) |
| shipping | `Wilaya`, `Commune`, `StopDesk`, `CarrierGeoMapping`, `GeoCodeChange`, `StorePrice`, `StoreShippingSettings`, `RateCard`, `CarrierSuggestionSettings`, `CarrierAccount`, `Shipment`, `TrackingEvent`, `OutboxEvent` | none stored (recipient passes through to the carrier) |
| payments | `Parcel`, `Payout`, `LedgerEntry`, `MoneySettings`, `OutboxEvent`, `ProcessedEvent` | none |
| notifications | `NotificationSettings`, `NotificationTemplate`, `OptOut`, `Parcel` (public code per shipment), `Message` | opt-out phones only |
| integrations | `ShopConnection`, `ImportedOrder`, `OutboxEvent`, `ProcessedEvent` | shop order ids and problem notes; contacts only in the outgoing event |

## 3.6.2 Data rules

| Id | Requirement | Status |
|---|---|---|
| DAT-001 | Every business row shall carry `storeId`; unique keys and indexes start with it. Reference data (geography) is global. | ✅ |
| DAT-002 | Ids are UUIDs generated by the service; customer-facing refs are store-unique and human-readable. | ✅ |
| DAT-003 | Money is stored as integer dinars (`Int`); message cost as integer centimes. | ✅ |
| DAT-004 | Times are `timestamptz` (UTC); business days and quiet hours are computed in `Africa/Algiers`. | ✅ |
| DAT-005 | Phones are normalised to E.164 (`+213...`) before storage and comparison. | ✅ |
| DAT-006 | Statuses are stored as strings validated by the contracts' enums; transitions are enforced in the domain, not by the database. | ✅ |
| DAT-007 | Orders are soft-deleted (`deletedAt`); every other delete is a hard delete unless audit requires history. | ✅ |
| DAT-008 | Secrets (carrier credentials, shop tokens) are stored encrypted with a wrapped data key and the KEK id (`kekId`, `wrappedKey`, `secret`), with a non-secret `hint` for display. | ✅ |
| DAT-009 | Tokens (refresh, verify, reset, invitation, self-confirm) are stored only as hashes. | ✅ |
| DAT-010 | Migrations are forward-only, run by a `<service>-migrate` job before the new image starts, and must work with the previous image still running (expand, then contract). | ✅ |
| DAT-011 | The geography dataset is versioned (`datasetVersion`, `retiredIn`) and seeded idempotently. | ✅ |
| DAT-012 | Payments only knows parcels created after it was deployed; older parcels need a one-off backfill script. | 🟡 (script ⬜) |

## 3.6.3 Retention

| Data | Kept | Then | Status |
|---|---|---|---|
| Audit events | 24 months | deleted | ✅ |
| IP address on an audit event | 90 days | set to null | ✅ |
| Refresh tokens | 30 days after issue | expired; revoked families kept for reuse detection | ✅ |
| Invitations | 7 days | expired | ✅ |
| Orders and customer data | while the store is active, then per legal advice (proposed: 3 years after delivery, then anonymised) | TBD-07 | ⬜ |
| Messages (no text, no phone) | 12 months proposed | deleted | ⬜ |
| Tracking events | with the shipment | deleted with the store | ⬜ |
| Ledger and payouts | 10 years (commercial records, proposed) | archived | ⬜ |
| Redis streams | about 100,000 entries per stream | trimmed (`MAXLEN`) | ✅ |
| Database backups | 35 days (bucket lifecycle) | deleted | ✅ scripts |

## 3.6.4 Data quality

- Address matching (INT-005) and `impossible_address` (FRD-001) keep wilaya and commune codes consistent with the geography.
- Unknown carrier labels are reported (`shipping.carrier-status.unknown.v1`) so the status map stays complete.
- Payout lines that match nothing are kept in `unallocated`, never dropped, so totals always reconcile.
- Data that feeds the risk score and analytics (status history, refusal reasons, call outcomes) is collected from Phase 1, even before the models use it.
